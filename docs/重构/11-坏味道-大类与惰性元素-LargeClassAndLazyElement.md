# 大类 + 惰性元素（Large Class / Lazy Element）

> 来源：《重构：改善既有代码的设计》Martin Fowler 第 3 章 —— 坏味道清单第 16、17 位（合讲）
> 跨书联动：《敏捷》SRP——一个类一个变化原因；提炼类（Extract Class）/ 内联（Inline）

---

## 一、坏代码场景

3000 行的上帝类——输入、音频、成就、存档全在它肚子里：

```csharp
public class GameManager
{
    // 什么都是它的：输入、音频、成就、存档……3000 行
    public int Score;
    private bool _paused;

    public void Update()
    {
        HandleInput();       // 输入处理
        UpdateAudio();       // 音频控制
        CheckAchievements(); // 成就检查
        SaveIfNeeded();      // 存档
    }

    public void HandleInput() { /* 读手柄/键盘 */ }
    public void UpdateAudio() { /* 音量、BGM 切换 */ }
    public void CheckAchievements() { /* 分数成就 */ }
    public void SaveIfNeeded() { /* 写档 */ }
}
```

旁边还有一个「惰性元素」——什么都不干的类：

```csharp
public class ScoreDisplay
{
    public void Refresh() { }   // 空的——什么都不干
}
```

## 二、问题

1. 这段代码有什么问题？当需求变化时，具体会在哪里崩盘？
   （提示：改音频逻辑要进 GameManager 翻几千行；改存档也要进 GameManager——**每一个**功能的变化都在同一个类里——这是 Day 6「发散式变化」的极限形态（SRP 最彻底违背：一个类装着所有变化原因）。
   类里哪些字段/方法天然是一伙的？（输入 / 音频 / 成就 / 存档）——一伙的成员怎么搬出去？
   `ScoreDisplay.Refresh()` 空方法——一个什么都不干的类，是「未来会用到」的自我安慰还是真实需求？）

## 三、你的回答（2026-08-06，同步自 00-我的回答.md「大类惰性元素」）

### 第 1 轮
1. 大量的不同可抽象的系统逻辑放在一起，单文件管理过多系统 查找修改都变得困难
   如果每个系统又分成多个小方法 在开始的时候没有进行 管理顺序后续维护的困难程度陡增
2. 暂停bool 音频
   积分Score 成就
3. 暂时没有用处的类删掉 真的有需要的时候再添加

### 第 2 轮（纠错补答）
- 具体崩盘点：改动不同系统需求时都会来改动这个文件；查找改动需求要翻很多行代码；版本容易冲突
- 重构手法：创建对应独立系统类管理自己的属性和方法；抽离时不动原本代码逻辑、代码顺序

## 四、标准解（2026-08-06）

### 1. 诊断（原文锚定）
- 《重构》第 3 章 Large Class：「类承担了太多职责，通常是过多的字段与方法。」它是「发散式变化」（Day 6）的**极限形态**：N 个变化原因全挤在一个类里 → 任何一个需求（新成就 / BGM 淡入 / 新存档槽）都要进同一坨代码翻找 → 多人改动必然版本冲突（你补答的两个点全中）。
- 与《敏捷软件开发》SRP 联动：**一个类只有一个变化原因**——上帝类的每个字段/方法都想有自己变化的原因。
- 归伙判据 = **高内聚**：一起变化的成员放一起（`_paused` 跟音频一起变 → 归音频；`Score` 跟成就一起变 → 归成就）。

### 2. 手法一：提炼类（Extract Class）——《重构》第 7 章
- 把高内聚的一伙字段+方法**剪切搬进**新类，原类持有新类实例（组合，GameManager 变编排器）
- **铁律：只拆不换**——行为、调用顺序、数值一律不变（重构的定义就是不改变外部行为，《重构》开篇原话）
- 你的实现完全符合：4 个系统类 + Update() 顺序原样 + 字段归伙正确

### 3. 手法二：内联/删除（Lazy Element）——《重构》第 3 章
- Fowler 原话精神：**让一个结构有存在价值的最有力证据，是它真正承担了什么责任**；"未来可能用到"的类是自我安慰
- `ScoreDisplay.Refresh()` 空壳 → 直接删除（YAGNI）。你答对了。
- 若空壳已被引用：先「内联类（Inline Class）」把内容并入调用方，再删。

### 4. 验收点评
- ✅ 提炼类：InputSystem / AudioSystem / AchievementSystem / SaveSystem 四个职责各一伙
- ✅ 字段归伙：`_paused`→AudioSystem、`Score`→AchievementSystem（与概念回答一致）
- ✅ 只拆不换：Update() 四个调用顺序一字未变
- ✅ 惰性元素：ScoreDisplay 已删除
- 小建议（装饰性）：`using System;` 已无引用可删；真项目里 GameManager 到此就是纯编排器，是理想形态
